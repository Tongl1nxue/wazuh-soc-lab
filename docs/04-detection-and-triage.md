# 两类事件研判、自定义规则和误报分析

日期：2026-11-08，时间按 Asia/Shanghai。环境保持 Wazuh 4.14.9、Filebeat 7.10.2；只向现有 Ubuntu 的回环地址发起请求。以下均来自真实请求和实际索引查询。候选规则回放明确属于真实日志的重放测试，不是新的实时攻击证据。

## 范围与资源

执行前 guest 可用内存 5174 MiB、剩余磁盘 37.4 GiB，三组件运行，Nginx 配置检查通过。规则 100110 无冲突；manager 没有启用的自动响应动作绑定。本轮没有安装新平台、升级版本、修改防火墙或改变网络。

先生成 5 个 Web 基线请求；实时验证两批各 5 个 Web 请求、各 6 次 SSH 连接，第二批用于修复归档后的复测。因此本模块总共 12 次无效用户名 SSH 连接，不应只报告总共 6 次。另有一次正常请求用于归档修复验证，查询/管理连接会生成额外正常 SSH 日志。实验次数不等于所有系统日志条数。

最终通过批次：`soc-detect-1d64d29b1512`。HTTP 请求、源日志、归档、告警均已对账；最终磁盘剩余约 38.2 GiB。公开证据见 `evidence/detection/verification.json`、`events.json`、`replay-matrix.json`；原始 JSON、完整 logtest 输出与连接错误保存在 `local-evidence/detection-lab`，不发布。未生成截图。

## 事件一：SSH 无效用户名连接

**发现。** 在 guest 中用一次性不存在用户名，对 127.0.0.1:22 顺序建立 6 次 SSH 连接，每次间隔约一秒，采用 BatchMode 和仅公钥认证；不进行密码猜测、不创建账户、不更改凭据。运行前用 getent 确认该用户名不存在。

**证据。** 最终批次客户端 6 次均非零退出；索引复核到 auth.log 的 6 条 `Invalid user` 原始日志，以及 6 条规则 `5710` 告警。只统计 `agent.name=soc-ubuntu`、`location=/var/log/auth.log` 和本次唯一测试用户名；journald 的同类数据没有重复计入。告警编号完整保存在 verification.json，例如 `1794126908.223173`、`1794126914.232903`。

**研判。** 规则 5710 指示不存在用户的登录尝试；多次出现需要核对来源、目标账户、频率、成功登录和授权背景。本次已知由实验脚本在本机发起，判定为授权模拟活动。该实验能证明检测无效用户连接，不能描述为口令爆破成功；没有触发或验证聚合爆破阈值，也没有证实入侵。

**误报背景。** 管理员输入错误用户名、失效的自动化账户也可能产生相同规则。规则命中本身是准确描述日志；若将所有此类告警直接升级为恶意入侵，研判结论会错误。

**处置与边界。** 实验脚本执行完毕后没有继续发起该批次连接；保留证据并标记授权测试。本轮没有执行 IP 封禁、真实密码轮换或账户停用。正常 SSH 成功采集此前已独立验证，不能将这些管理登录误认为该不存在用户名认证成功。此研判是实验记录，尚不是已完成审批的生产工单。

## 事件二：Web 环境配置路径请求

**发现。** 最终批次向自有 Nginx 请求 5 条路径，并为每条附加同一批次标记：

| 路径 | 实际 HTTP 状态 | 调优规则回放结果 |
| --- | --- | --- |
| /index.html | 200 | 31100，level 0，不产生安全告警 |
| /ordinary-missing-page | 404 | 原生 31101，level 5 |
| /docs/.env-guide | 404 | 原生 31101，不命中自定义规则 |
| /.env | 404 | 自定义 100110，level 7 |
| /.env.example | 404 | 原生 31101，不命中自定义规则 |

**证据。** 本批 5 条访问均在 archives 查到，实时自定义告警 1 条，编号 `1794126908.218582`，时间 `2026-11-08T08:35:08.175+0000`（本地 16:35:08.175），状态 404。四条负例在已采集 archives 中没有被归类为 100110。原生 31101 仍可能为普通 404 产生告警；“自定义规则未命中”不等于“没有任何告警”。

**研判。** 请求 /.env 可以是寻找环境配置文件的行为，但本次属于授权实验。404 只说明本次资源未找到，不能证明攻击成功、所有敏感文件都安全，或防火墙阻断。Nginx 没有因本模块新增阻断策略；规则描述中的 Denied 是告警文字，不代表 IPS 成果。本轮只验证检测。

**处置与边界。** 保留对应请求、状态、日志路径和告警编号；本次返回 404，未观察到响应中敏感配置泄露。没有执行第三方扫描，没有尝试利用应用漏洞。真实环境应进一步核对访问背景、成功响应、文件暴露与代理路径；这些生产处置没有被本实验代替。

## 自定义规则原理与误报调优

实际部署规则源码：`config/rules/soc_web_rules.xml`。它继承 4.14.9 的 Web 4xx 规则 31101，要求状态码精确为 404，且 URL 满足 `^/\.env(?:\?.*)?$`，将事件提升为 level 7。规则无需额外实验标记即可命中 /.env，因此后续真实同路径请求也会被检测。

最初候选仅用 `\.env` 匹配子串，在同一组真实访问日志的 logtest 重放中，/.env、/docs/.env-guide、/.env.example 都命中 100110。已知的文档路径对照因此被不必要地提升；边界路径也被扩大包含。

调整为路径起止边界并保留查询参数支持后：正例 /.env?参数 命中；普通 200、普通 404、文档路径、后缀示例路径四个对照均不命中自定义规则。不要从 5 个实验样本推断生产误报率。/.env.example 被排除是本规则范围选择，不保证该路径在所有环境中安全；编码变体、其他目录下 .env、HTTP 200 暴露及其他敏感文件不在本规则覆盖范围。

## 实际问题与修复

1. **回放验收读取问题。** 当前版本 wazuh-logtest 将输出写入 stderr。初版验收脚本只解析 stdout，因此误报“回放失败”。检查实际输出后修正为合并解析两条输出流，复用原始日志重新验证；未把脚本失败当作检测引擎失败。
2. **重建后归档转发丢失。** 首次实时批次已有规则 5710 和 100110 告警，但 archives 查询未找到该批 Web 记录。实际检查为 manager logall_json=yes，而 Filebeat 配置 archives=false；此前只验证 restart，没有证明 recreate 后仍生效。
3. **持久修复与复测。** 备份原启动脚本及 Compose，将当前固定镜像的 Filebeat 服务启动脚本通过只读挂载保留，使用其支持的 `-M wazuh.archives.enabled=true` 覆盖开关。重建 manager 后用一次新正常请求验证，再重复有限异常批次，最终五条 archives 和实时告警均通过。-M 不会改变基础配置文件本身，检查有效状态不能只看 YAML 中的 false；需要看启动覆盖及实际索引结果。初始化为什么重置基础值的更深原因尚未定位，不写成已证实结论。

Filebeat 参数依据：[7.10 官方命令参考](https://www.elastic.co/guide/en/beats/filebeat/7.10/command-line-options.html)。规则参考：[4.14.9 Web 规则](https://github.com/wazuh/wazuh/blob/v4.14.9/ruleset/rules/0245-web_rules.xml)、[4.14.9 SSH 规则](https://github.com/wazuh/wazuh/blob/v4.14.9/ruleset/rules/0095-sshd_rules.xml)。

## 持久化与恢复

备份位置为 guest `/opt/soc-lab/detection-lab/backup`：原规则目录、原 Compose、归档修复前 Compose、Filebeat 服务启动脚本，以及 SSH/Nginx 配置观察值。运行期规则保留在命名卷；规则源码另外通过 `config/soc_lab/soc_web_rules.xml` 只读挂载到 manager。Filebeat 启动脚本同样从该持久目录挂载。未修改 SSH 或 Nginx 配置。

如需仅撤回本模块自定义规则，在 Windows 项目目录执行：

```powershell
python scripts/lab_transport.py scripts/detection-lab.py --argument restore
```

该操作恢复原 Compose 的规则部分、移除本实验专用规则文件，保留独立的 archives 修复和原始证据；会重建/重启 manager。只有确认要移除 archives 启动覆盖时，单独执行：

```powershell
python scripts/lab_transport.py scripts/fix-archive-persistence.py --argument restore
```

后者可能让 archives 转发恢复关闭，执行后应重新验收。它的备份包含自定义规则挂载，若已经先撤回规则，再执行该操作会重新引入当时的挂载；需要按实际变更顺序倒序恢复，不能不看当前状态重复套用旧备份。当前恢复入口已实现，但本轮没有实际撤回成功配置来验证完整恢复流程。
